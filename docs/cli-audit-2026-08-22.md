# railctl CLI audit

Audited against `~/Developer/CLAUDE.md` "CLI Design (agent- and script-friendly)" (bundled as
`rules.md`). 34 rule clauses judged. Evidence: the captured bundle in this directory plus read-only
inspection of `/Users/jacoren/Developer/Personal/railctl` source and tests. **The `railctl` console
script was never invoked and no file in the project was modified.**

Audited on 2026-08-22 against commit `5e10962`.

**One caveat about the evidence, which materially affects how to read it.** The bundle was
captured in a shell where `FORCE_COLOR=3` is set, and Typer's Rich renderer treats that as a
terminal. Every ANSI count taken from the bundle is therefore inflated, and the one colour finding
raised from it was overturned for exactly that reason (§5). Two findings that survived were
re-checked afterwards in a shell with `FORCE_COLOR`, `PY_COLORS` and `CLICOLOR_FORCE` unset, and
both hold: `railctl --help` on a non-TTY emits zero ANSI sequences, and it still wraps to 80
columns (47 lines exactly 80 characters) and still truncates `backup --out`'s default to
`railctl-backups/loco-<address>-<set>.js…`. A refinement on G5 found in that re-check: the
manifest publishes `--out`'s default as `null`, so the full default path is available to a caller
in NO form - truncated in the help, absent from the manifest.

Any future finding that rests on an ANSI count must be re-taken in a clean environment before it
is believed.

## 1. Verdict

railctl meets most of the bar it set itself, and meets the hardest parts of it well: one JSON value
on stdout, a versioned envelope, a fixed five-field error shape with 41 frozen machine-readable
codes, `suggestions` as argv arrays everywhere, a generated manifest that answers with nothing
plugged in, and a single metadata table that provably drives both the parser and the manifest. Those
are the parts most CLIs get wrong, and here they are pinned by tests that would fail on a rename.
The failures are concentrated in three places. First, the exit-code contract is the rule's opposite:
21 published codes where the convention names six, eleven of them pure domain detail promoted into
the process status, and three of the six conventional numbers (4, 7, 130) meaning something else in
railctl than they do in the rules — an agent applying the convention will retry a permanently
unsupported request and will wait for a 130 that never arrives. Second, long-running work is not
modelled as a resource at all: a 41-minute `backup --all` that is killed rather than interrupted
leaves no artifact and cannot be resumed. Third, safety scaling stops one tier short of where it
matters — `railctl cv write 8 8 --yes` factory-resets a decoder on a bare `-y`, while the
comparatively safe `restore` correctly demands an unguessable serial token. Everything else is
either a documentation gap, a coverage gap (`--dry-run` on one of eight mutating commands,
`changed` on two of the desired-state verbs), or a rendering defect (`--help` hard-wrapped to 80
columns when stdout is not a terminal, destroying one published default value outright). None of the
gaps is a correctness bug in the protocol layer; all of them are contract-surface gaps that an agent
or script consuming this tool would hit.

## 4. Surviving gaps, ordered by what a caller loses

### G1 — Long-running work is not a resource (T2, **fail**, effort: large)

**What a caller experiences.** `railctl backup --all --yes` runs for 41 minutes (measured:
docs/probe-results.md:1209). If the connection drops or a parent process is reaped, there is nothing
to reattach to and nothing to collect: no `operation_id`, no `get`, no `wait --timeout`, no `cancel`,
no `logs --follow`, and no `--timeout`/`--wait`/`--follow` among the global options. On SIGINT the
partial document is written with `"interrupted": true` and exit 9. On SIGHUP/SIGTERM/SIGKILL —
an ssh drop, a killed parent, a harness reaping the process group — nothing is kept at all: there is
no signal handler and no `atexit` writer anywhere in `src/`, and the document is assembled only at
the end or in the `KeyboardInterrupt` path. Forty-one minutes of decoder reads are gone. Even the
graceful partial file cannot be continued: `--force` only overwrites, there is no `--resume`.
The ndjson per-CV stream is a real mitigation, but a truncated ndjson stream is not a
`railctl/backup/v1` document and no command converts one, so `restore` and `diff` cannot consume it.

**Fix.** Two steps, cheapest first. (1) Make existing runs survivable: handle SIGTERM/SIGHUP the way
SIGINT is already handled, checkpoint the partial document every N CVs so even a SIGKILL leaves a
readable file, and add `backup --all --resume <file>` that skips every row not marked "not
attempted". That alone turns a lost 41 minutes into a lost 30 seconds. (2) Then the rule's literal
shape: a `railctl operation` noun over a small on-disk run directory — `--detach` returning
`{"operation_id": …}`, plus `operation get|wait --timeout|cancel|logs --follow` replaying the ndjson
the run already produces. Specify `cancel` as "stop after the CV in flight", since a service-mode
operation holds the station lock for up to 95 s.

### G2 — The most destructive write is gated only by a bare `-y` (S4, **partial**, effort: medium)

**What a caller experiences.** `railctl cv write 8 8 --yes` factory-resets the decoder — the tool's
own prompt says "every setting is wiped" — because `confirm()` returns immediately when
`settings.assume_yes` (deps.py:667). An agent or wrapper that pins `--yes` in a prefix argv, which is
the normal way to make a CLI scriptable, silently authorises the wipe. The same bare `-y` authorises
moving a locomotive's address (CV1/17/18/29) and moving the ZIMO index bank (CV31/32), after which
every later indexed read and write lands somewhere else. There is no second gate: `catalog/zimo.toml`
gives CV8 no min/max so the range check never fires, and `restorable = false` only stops `restore`.
`tests/cli/test_cv.py:1171` pins that `--yes` answers a confirmed-CV prompt, so this is tested
behaviour, not an oversight. The risk ordering is inverted: `restore`'s serial mismatch — writing
known-good values onto a backed-up decoder — earns an unguessable token, while the irreversible wipe
earns the same `-y` as `cv write 3 20`.

**Fix.** Refuse `cv write 8 8` unless `--confirm=<value just read from CV8>` or
`--confirm=<serial from CV251-253>` is supplied, printing the token in the refusal exactly as
`_check_serial` already does; `serial_token()` is public and already exists. Apply the same to
CV31/CV32, whose damage is silent and delayed. Make the manifest's `confirms` field per-condition
rather than one boolean per command.

*(The auditor also flagged `power resume`, `doctor --power-on` and `doctor --measure-status-bits`.
Dropped on check: `power resume` is the routine per-session release and confirming it would train
reflexive `-y`; the two doctor flags are opt-in and name their own hazard. The finding stands on
`cv write` alone.)*

### G3 — The exit-code contract is the rule's opposite (E5, **fail**, effort: large)

**What a caller experiences.** An agent must carry a 21-branch table where the convention promises
six, and the branch it needs is duplicated — `decoder_no_ack` is reachable both as exit 10 and as
`error.code`. Worse, an agent applying the convention's own numbers misreads three of them: exit 4 is
`protocol`/`xbus_*`, not "not found" (`port_not_found` is 3); exit 7 is `unsupported_feature` with
`retryable: false`, so a caller treating 7 as transient retries a permanently out-of-scope request
(the actually retryable codes are 5, 12 and 3); and 130 is deliberately never emitted — `main()`
converts typer's sentinel into exit 9, so a caller waiting for 130 on Ctrl-C waits forever. Only 0, 2
and 8 mean what the rules say. Exit 9 is additionally overloaded: for `backup` it is a delivered
result on stdout with a `backup.incomplete` warning and no error envelope; elsewhere it is a real
error envelope on stderr. `errors.py`'s own docstring says new domain detail belongs in `error.code`
"not in a new exit code" — and then freezes 10–20 anyway. The "documented" half of the rule is met
exemplarily: every command's `--help` carries a generated EXIT CODES section and the manifest
publishes both per-command codes and the 41-row error table.

**Fix.** Not fixable inside this major version — the codes are a declared frozen contract. For v2:
collapse 10–20 into the convention's numbers (7 for `link_timeout`/`station_busy`/`port_busy`, 4 for
a resolved-but-absent target, 8 for partial, one domain-failure code otherwise), leave the 41-row
`error.code` table as the sole home for domain detail, and emit 130 for an interrupt while keeping
`code: aborted`. Until then, state the divergence in one line in the manifest and the root help so
the mismatch is documented rather than discovered.

### G4 — Half the published examples cannot be pasted (D6, **fail**, effort: medium)

**What a caller experiences.** Every EXAMPLES block is generated by `_meta._example()`, which
substitutes argument *names* in angle brackets. The root block shows
`railctl power <state> --format json`, `railctl cv read <cvspec> --format json`,
`railctl cv write <cv> <value> --format json`, and four more; on each of those command pages plus the
`cv` group page the placeholder line is the **only** example. Pasted verbatim, `<state>` is a shell
redirection from a file named `state`, and `cv write <cv> <value>` additionally truncates a file
named `value`. `behaviour.txt:10` shows a missing-argument error routing the caller to exactly such a
page. `tests/cli/test_schema.py:377` pins this shape, so it is intended rather than drift. The
literal grammar does exist elsewhere — `cv read --help`'s argument help gives `29`, `3-8`, `1,3,29`,
`accel_rate` — just not under the heading the rule governs.

**Fix.** Add `examples: tuple[str, ...]` to `CommandMeta` with hand-written literal invocations per
row, emit those from `help_epilog`/`group_epilog`/`root_epilog`, and replace the existing test with
one that parses each example through the Click tree via `Command.make_context` (no execution) and
fails if it does not resolve. A non-runnable example then becomes a red test.

### G5 — `--help` is wrapped, and one default value is destroyed, when stdout is not a TTY (D3, **fail**, effort: small)

**What a caller experiences.** The bundle was captured with stdout redirected to a file, so nothing
was a TTY, and every page is still laid out to exactly 80 display columns (537 lines exactly 80
bytes; panel rules 240 bytes of box-drawing). The wrapping folds real content: the root OUTPUT
sentence splits as `… see railctl` / ` schema`, so grepping the page for `railctl schema` finds
nothing; `backup`'s exit-9 meaning is broken across nine lines. One fact is not merely folded but
lost: `backup --out`'s default renders as `~/railctl-backups/loco-<address>-<set>.js…` with a Rich
ellipsis, and the full string appears zero times in help-plain.txt against once in manifest.json.
Cause: `context_settings={"max_content_width": 100}` caps but never disables wrapping, and Typer's
Rich renderer falls back to Rich's 80-column default when the stream is not a terminal. Nothing in
`cli/` consults `isatty()` for width, and no test pins help width.

**Fix.** At startup, when `sys.stdout.isatty()` is False, set `typer.rich_utils.MAX_WIDTH` (or the
`TERMINAL_WIDTH` env var it reads) to a very large value and raise `max_content_width` on both
`main.app` and `cv.cv_app` to match. Add a test that renders `--help` for every `COMMANDS` row on a
non-TTY stream and asserts no line exceeds the longest single metadata help string.

### G6 — Seven of eight mutating commands cannot be planned (S1, **partial**, effort: medium)

**What a caller experiences.** For `cv write` — the command that permanently changes a decoder —
there is no way to learn what an invocation would do without doing it. Slug resolution, the byte
range check, the catalog min/max check that raises exit 15, the `--verify` + `--track main` conflict,
`CONFIRM_CVS` membership and `require_address` all happen only inside `work()`. An agent validating a
batch of writes must run them or reimplement the catalog. `power on` has the same hole with a
physical consequence: a caller cannot ask "what would this do" and be told "energise the track,
stop-all, idle loco N, leave it HELD" — it can only find out by energising the track. Where
`--dry-run` exists it is exemplary: `_RestoreRun.execute` runs the identity gate, page gate, unlock
check, live reads and `plan_restore`, then returns before the first write, and three tests pin that
the dry plan equals the real plan with zero writes and zero selector telegrams.

**Fix.** Make `--dry-run` a global option honoured by every `mutates: true` command, returning the
same `CommandResult` shape with `dry_run: true` and no telegram sent — `restore` already proves the
one-planner/two-consumers pattern. For `cv write` the plan needs no station at all. For `power` and
`doctor` the plan is the step list they already publish after the fact. Add `supports_dry_run` to the
manifest beside `mutates`/`confirms`.

### G7 — `restore` refuses late, after minutes of programming-track occupancy (S3, **partial**, effort: small)

**What a caller experiences.** A scripted `railctl restore loco3.json --format json` with no `--yes`
and no terminal opens the port, prints the programming-track notice, runs the full identity gate and
reads every planned CV (~2.4 s each; roughly 3 minutes for a 77-CV backup) before exiting 2 with
"rerun with `--yes`". The answer was fully determined at argument-parse time: `assume_yes` is False
and `interactive` is False, and nothing read from the decoder can change it. Nothing is written, so
this is cost and CI/cron timeout risk rather than a hazard. The tool holds itself to the opposite
standard elsewhere: `cv write` gates before `open_station`, with a comment saying "a refusal must
cost no port" and a test that makes `Station.open` raise.

**Fix.** In `_RestoreRun.execute`, before `check_identity`, raise the same
`ConfirmationRequiredError` with the same `retry_argv` when
`not dry_run and not assume_yes and not interactive`, phrasing the question from the file's CV count
rather than a measured estimate. Keep the late `confirm()` for the interactive case, where the
measured estimate is the whole value of the prompt. (`backup` was checked and is exempt: whether a
confirmation is needed depends on `sweep_bound(mode, station.capabilities)`, which is genuinely
unknowable before the port opens.)

### G8 — Non-zero exits do not imply empty stdout (E1, **partial**, effort: small)

**What a caller experiences.** A caller following "non-zero exit means stdout is empty, read stderr"
is wrong in two ways. In `--format ndjson`, a mid-run failure leaves the already-written event lines
plus the closing `summary` on stdout alongside the stderr envelope. More surprisingly, the buffered
path does the same: `_errors.run()`'s success branch renders the `CommandResult` to stdout and exits
with `result.exit_code`, which is routinely non-zero — exit 8 for a partial throttle sequence and
exit 9 for an incomplete backup both put the whole result envelope on stdout with `render_error`
never called and **stderr empty** (`tests/cli/test_backup.py:1305-1312` asserts
`result.stderr == ""`). Errors themselves never reach stdout and the exit status always matches the
report; it is "empty stdout" that does not hold.

**Fix.** The ndjson half is forced by the NDJSON rule in the same rules.md and should be kept but
published: add one line to `_meta._output_lines` and a manifest field saying that in ndjson mode
stdout carries the pre-failure events and a terminating `summary` whose `exit_code` matches the
stderr envelope. The buffered half is a free choice — either mirror an error envelope to stderr on
non-zero buffered exits, or document exits 8 and 9 as "result on stdout, stderr silent" in the same
place. `railctl monitor --help` already documents its Ctrl-C case; nothing else does.

### G9 — Two desired-state verbs never say whether anything changed (S5, **partial**, effort: medium)

**What a caller experiences.** `build_cv_write` publishes `cv, name, value, mode, track, address,
verified` and no `changed`, and `station.cv_write` is called with no preceding read — so writing a CV
that already holds the value is indistinguishable in the envelope from a write that moved it. An
agent reconciling a decoder against a desired CV set must issue a separate `cv read` before every
write. `build_function` publishes exactly `{address, function, requested, now_on}`, pinned by an
exact-dict test, and `now_on` is the resulting state, not whether it moved — even though
`Station._function_set_group_path` reads the current group with `refresh=True` before flipping the
bit and then discards the prior value. `drive` and `power` do this correctly, tri-state, with `null`
rather than a guessed `false`; `build_power`'s own docstring names the exact failure
("`power on` reported `true` unconditionally, which is not what a desired-state verb owes a caller")
without carrying the reasoning to these two.

**Fix.** Publish tri-state `changed` on both. For `function`, compare the pre-read group against
`requested`, and use `null` on the `single_function_cmd` path that skips the read. For `cv write`,
add a pre-write read on the path that already reads back for `--verify`, with `null` when
`--track main` made a read impossible. `stop` is arguably exempt as an event rather than a state;
saying so in its help would settle it.

### G10 — No `--fields`, and one unbounded command with no default cap (O7, **partial**, effort: large)

**What a caller experiences.** No command anywhere accepts `--fields`, so `doctor --json`,
`backup --json` (65 curated rows, each with cv/name/status/value/detail/attempts/elapsed_ms) and
`schema --json` are all-or-nothing. `railctl schema "cv read"` returns 8173 bytes for a command
definition that is 970 bytes compact — the rest is the 41-row error table (5468 bytes) and the global
options (1564), and `_meta.py:1450-1462` documents that as intentional. Separately,
`monitor --json` with no `--limit` buffers every broadcast until Ctrl-C and then emits them in one
envelope plus the full `known_events` vocabulary; nothing auto-bounds it when stdin is not a TTY. The
other three clauses are genuinely met: filtering happens inside the tool (cvspec ranges and catalog
slugs, curated-by-default backup with `--all` behind a confirmation, `--with-address`/`--include-sweep`
gates, per-command schema lookup), and names are semantic throughout.

**Fix.** Two separable changes. (1) Add `--fields` driven from the same `_meta` rows that generate
help and the manifest, projecting `result` before `render()` sees it — one implementation covers
every command; at minimum ship it on `schema`, `backup` and `doctor`, and put `error_codes` behind
`--with-error-codes` for a per-command lookup. (2) Give `monitor` a small default `--limit` in JSON
mode — the mode that cannot show anything until it ends — leaving human and ndjson unbounded.

### G11 — Warnings land in the human result stream (O1, **partial**, effort: small)

**What a caller experiences.** `railctl power resume > out.txt` or `railctl cv read 29 > value.txt` in
the default human format puts `warning: stored_speeds_released: …` and `warning: cv.stale_result: …`
in the same file as the result. `_render_human` (render.py:51-58) writes warnings to stdout, and two
tests pin it deliberately on ordinary success paths. Every other category the rule names is on the
correct stream: logging via `configure_logging(…, sys.stderr)`, every progress and notice print with
`file=stderr`, and errors only through `render_error` to stderr. In JSON/NDJSON the warnings sit
inside the single envelope value that the neighbouring rule requires, so those modes are in genuine
tension between two rules; the human renderer has no such tension and still chose stdout.

**Fix.** Move the `for warning in result.warnings` loop in `_render_human` onto a stderr stream —
`_errors.run` already holds both stream handles in `OutputContext` — and update the human-format
warning assertions in `tests/cli/test_format_modes.py` and `tests/cli/test_throttle.py`. The
JSON/NDJSON `warnings` array stays where it is.

### G12 — `monitor --format ndjson` carries no version string (O5, **partial**, effort: small)

**What a caller experiences.** A consumer of `railctl monitor --format ndjson` cannot tell v1 lines
from a future v2: `stream_monitor` writes only `event` lines and a `summary` of
`{count, complete, exit_code}`, with no `start` line and no `schema` key anywhere.
`MONITOR_SCHEMA` is referenced only by the human/json path, and the two summary assertions in
`tests/cli/test_monitor.py` are full dict equalities, so the absence is pinned. Every other stream in
the tool does carry it: backup, diff and restore each put `schema=` on a `start` line, the
non-streaming ndjson path passes the whole envelope through the summary, and
`railctl monitor --format json` emits `railctl/monitor/v1`.

**Fix.** Emit a `start` event at the head of `stream_monitor` carrying `schema=MONITOR_SCHEMA` and
the run parameters, matching the other three streams; update the two exact-dict assertions.

### G13 — Discovery grammar and invocation grammar disagree (D10, **partial**, effort: medium)

**What a caller experiences.** The 14 paths mix three grammars: two are `noun verb` (`cv read`,
`cv write`), five are bare verbs with a positional (`drive`, `stop`, `restore`, `diff`, `backup`),
five are bare nouns (`status`, `version`, `schema`, `doctor`, `monitor`), and `power` and `function`
are nouns whose verb is a positional enum. The concrete cost: `railctl power on` is a valid
invocation, but `railctl schema power on` is exit 2 with `"power on"` reported as an unknown path,
while `railctl schema cv read` succeeds. An agent that reads a command line and asks the manifest
about it gets a usage error for two of the tool's nouns.

**Fix.** Do not rename the verbs — that breaks every existing invocation for a cosmetic gain. Either
register `power on|off|resume` and `function <id> on|off|toggle` as real subcommand paths while
keeping the current spellings, or make `schema` resolve a path whose trailing words are the values of
a leading positional enum. Then state the grammar in one line of root help so the mix is a declared
convention rather than an inference.

### G14 — Two of the five fixed headings are Click's and Rich's, not railctl's (D5, **partial**, effort: medium)

**What a caller experiences.** `help-plain.txt` contains zero occurrences of `USAGE`; `OPTIONS`
appears only inside the `[OPTIONS]` usage placeholder, never as a heading. A caller grepping the five
documented names finds `OUTPUT`, `EXIT CODES` and `EXAMPLES` (exactly 16 times each, spelled as the
rule requires) and misses the other two, which render as ` Usage: railctl …` and a box-drawn
`╭─ Options ─╮` panel. The project's own tests concede it: the test named
`test_help_..._carries_the_fixed_headings` checks only three, and another needs `.upper()` to find
"USAGE" at all.

**Fix.** Either override the two headings to the fixed spellings (Typer exposes the panel titles;
`Usage:` comes from `format_usage` on the already-subclassed group), or emit `USAGE` and `OPTIONS`
from `_meta` the way the other three already are. Then extend the per-command heading test to all
five. *(The auditor also flagged Rich's `Arguments` panel; dismissed — the rule requires five
headings to be present and does not forbid additional sections, and a `Commands` panel exists on the
same reasoning without being flagged.)*

### G15 — The CLI adapter is not thin (T4, **partial**, effort: medium)

**What a caller experiences.** An in-process second front end cannot ask for "back up this decoder".
The core offers `Station.cv_read_many` and the `railctl.backup` document types, but the run order
(index selectors, CV29, identity CVs, then the planned list), the neutral-page gate, the sweep bound
and the three-valued rows live only in private CLI modules — `commands/backup.py` is 1,497 lines,
`restore.py` 1,200, and `src/railctl/__init__.py` exports only `__version__`. The underscore is not
the real barrier; the coupling is: `_BackupRun.execute(self, station, output: OutputContext)` prints
to `output.stderr` and `_confirm_sweep` calls `confirm(..., stdin=sys.stdin, …)`, so the workflow
cannot run without CLI I/O objects and a terminal question. `_sweep.sweep_bound(mode, capabilities)`
settles it without any line-count argument: a pure function of measured hardware capability, sitting
in the CLI package. The other two elements of the rule are met outright — `_meta.py` is one metadata
source pinned in both directions, and layering is enforced mechanically by `tests/test_layering.py`.
The project already knows the right shape: `station/doctor.py` exports `run_probe` publicly, which is
why `commands/doctor.py` is only 532 lines of rendering.

**Fix.** Lift the run order into a public `railctl.backup.run` taking an open `Station`, a plan and an
event callback, returning a `BackupDocument`, leaving the CLI module with parsing, the confirmation
gate and rendering. Same for `restore.py`. Most of `tests/cli/test_backup.py` becomes core tests
unchanged, since it already drives a `FakeBackupStation`.

## 5. Raised and dismissed

**O6 — "Colour, spinners, progress bars and pagers only when that stream is a TTY; honour
`NO_COLOR` and `TERM=dumb`."** Reported as *partial* on the grounds that `help.txt`, captured with
stdout redirected to a file, contains 3856 ANSI sequences. Overturned: the audit environment sets
`FORCE_COLOR=3`, and Typer's `rich_utils` forces a terminal when `FORCE_COLOR`, `PY_COLORS` or
`GITHUB_ACTIONS` is set. The colour was forced by the capture environment, not by railctl. With those
variables unset, a Rich console on a redirected stream reports `is_terminal=False` and emits zero
escapes, and no ESC byte is baked into any help string. Both variables the rule actually names work
on the help stream: `TERM=dumb` yields zero sequences, and `NO_COLOR=1` removes every colour, leaving
only bold and dim attributes — which the `no-color.org` convention does not govern. railctl's own
output is stricter still: it ignores `FORCE_COLOR` entirely and stayed plain in the same capture
(`ansi_in_stderr=0` on all four probes). One narrower residual is real and worth noting without
counting against the rule: `GITHUB_ACTIONS` also trips Typer's force, and nobody opts into that, so a
redirected `--help` in CI does get escapes and `--color never` cannot reach Typer's console. That is
a third-party default in an environment whose log viewer renders ANSI, and both escape hatches the
rule specifies still work there.

## 6. Not judged from the evidence, and what would settle it

1. **Whether a real hardware run leaves the same bytes on stdout as the `CliRunner` tests show.**
   Finding G8 rests on test assertions and source reading, not a live capture. The command that
   would settle it: `railctl backup --address 3 --out /tmp/x.json --format ndjson` with both streams
   redirected to separate files. **Not run** — the station may be connected.
2. **Whether `monitor --json` under real broadcast traffic grows without bound in practice.** The
   code path in G10 is unambiguous (no cap, buffered until Ctrl-C), but the bundle contains no
   monitor capture, so the actual memory and token cost at, say, five minutes of layout activity is
   unmeasured. Settled by `railctl monitor --format json` redirected to a file, interrupted after a
   fixed interval, with the byte count recorded. **Not run.**
3. **The GITHUB_ACTIONS colour residual noted in §5.** Confirmed by reading Typer's source, not
   reproduced. A capture with `GITHUB_ACTIONS=true`, `FORCE_COLOR` unset and stdout redirected —
   `railctl --help > /tmp/help-ci.txt` — would confirm both that escapes appear and that
   `--color never` does not suppress them. **Not run.**
4. **The real cost of G7's late refusal on this decoder.** The ~3 minute figure comes from
   `docs/probe-results.md` (77 CVs, 185 s after the grouped-read optimisation), not from a timed
   run of the refusal path. `time railctl restore <77-cv-file>.json --format json < /dev/null`
   would settle it exactly. **Not run.**
5. **Whether a SIGTERM during a sweep truly leaves no artifact (G1). MEASURED 2026-08-22, and
   it holds.** A `railctl backup --address 3` on the programming track was killed by SIGTERM
   after roughly 120 s of a 190 s run — over half the reads done. No output file existed
   afterwards, not even a partial one, and a following `railctl status` reported
   `service_mode=False`, so the service session closed despite the signal. Both halves of G1
   are therefore confirmed rather than inferred: the session teardown is safe, and the work is
   lost in full. The note below records how the claim originally stood.

   Originally established by absence —
   no `signal`/`atexit` import anywhere in `src/` and a write path that only runs at completion or
   under `KeyboardInterrupt`. Confirming it empirically would require starting a real sweep and
   sending SIGTERM to it, which occupies the programming track for minutes. **Not run.**
6. **Mutation coverage of the contract tests.** The tests that pin the error codes, envelope key
   order and manifest/parser agreement were read and judged sound, but no mutation testing exists in
   this project yet, so "a rename would fail the test" is a reading of the test, not a measurement.
